> 面向对象：想研究/复用本程序数值核心的开发者。**这是四篇中最重要的一篇。**
> 程序位置：`09_wxxcx/utils/engine.js`（小程序版）与 `app.js`（Web 版）中的规则引擎同源。
> 完整规格见 `02_PRD/PRD_Trail_Lab_Engine_v2.0.md`。

## 〇、引擎是什么：一句话

`TrailLabRuleEngine` 是一个**确定性数值计算核心（纯函数）**：输入两份"画像"（用户 + 线路），输出一份**数值契约 JSON**。它不碰 UI、不调用 AI、不读写存储——同样输入必然同样输出。

```
compute(userProfile, raceProfile, weightKg) → 契约 JSON
```

引擎内部按固定顺序计算：**完赛时间 → 碳水 → 液体 → 钠 → 咖啡因 → 补给点**，每个输出都带 `evidence`（依据链）与 `confidence`（置信度）。

## 一、输入：两个画像

### 1.1 UserProfileBuilder（用户画像）

从 FIT 数据 + 手动输入构建，关键字段：

```js
{
  ability_score,        // 仅展示性汇总，不参与 V2 计算
  fatigue_risk,         // HRV 五档 → low/medium/high/severe
  terrain_speed,        // {climbVamMh, descentVamMh, flatPaceMinKm} 三独立速度参数
  vo2max, itra_points,  // 能力信号 B/C（缺失兜底用）
  physiological_max_hr, // 手动输入的生理最大心率（关键修复）
  verified_cho_max,     // 已验证碳水上限（肠胃约束核心）
  sweat_rate, sweat_sodium,  // 实测输入
  caffeine_habit, bmi, ...
}
```

**关键设计——能力分拆分**：V1 把"能力分"合成一个数字，V2 拆成三个独立速度参数（平路配速 / 上坡 VAM / 下坡 VAM），从单个代表性 FIT 文件按坡度分桶提取（爬升 ≥ +2% / 下降 ≤ −2% / 其余平路），**不合并**，直接进入分段计算。

**HRV 状态**：普通活动 FIT 文件不含 RR 间期/HRV 状态数据，因此由用户五档手动输入（平衡/不平衡/偏低/极差/无状态）映射 `fatigue_risk`。疲劳只修正**当日发挥**，不污染能力分。

### 1.2 RaceProfileBuilder（线路画像）

只含线路数据，不含用户能力。关键字段：

```js
{
  distance_km, ascent_m, descent_m,
  aid_stations_km,       // 官方 CP（含关门时间 → 节奏上限 + 携带量下限）
  climb_segments,        // [距离km, 爬升m] 分段（显式路段或归一化兜底）
  steep_segments,        // 坡度 ≥80m/km 的陡段 → 陡爬升前补给点
  supplemental_points_km,// 爬升触发 + 陡坡预补给
  climb_trigger_m,       // 累计爬升触发点（默认 250m）
  max_interval_min,      // 最大摄入间隔（默认 30min）
  expected_finish_time_h,// 用户填的期望完赛时间（最高优先级）
  weather_temp_c, humidity_pct,
}
```

**分段归一化**：若用户未提供显式路段，`normalizeSegments` 按固定比例拆分（35% / 35% / 30%），保证后续计算有分段可用，但会标注为兜底。

## 二、核心计算：完赛时间（四级分层估算）

这是引擎第一个、也是最关键的计算。优先级：

```
用户填写期望时间（user_input，最高优先级）
   ↓ 未填
① 地形分段分解（terrain）   — 爬升÷VAM + 下降÷VAM + 平路÷配速
   ↓ 地形数据不完整
② ITRA 保守兜底（itra_fallback）
   ↓ 无 ITRA
③ VO2max 粗略兜底（vo2max_fallback）
   ↓ 无 VO2max
④ 极端保守兜底（conservative）
```

### ① 地形分段分解

```js
// VAM 已隐含水平推进，不叠加平路当量（避免双重计费）
t_climb   = 总爬升 / 上坡VAM
t_descent = 总下降 / 下坡VAM
t_flat    = 平路距离 / 平路配速折算速度
```

**地形完整性检查** `terrainCompleteness`：爬升/下降 >50m 且平均坡度 >3% 时，若对应 VAM 缺失 → 不静默丢弃，降级到兜底。平路缺失同理。

### ② ITRA 保守兜底

```js
// ITRA km-effort 惯例：100m 爬升 ≈ 1km 水平
effectiveKm = distance_km + ascent_m / 100
// PI → 有效速度线性映射（PI 300→7.0，1000→10.5 km/h）
speedKmh = 7.0 + (PI - 300) * 0.005
est = effectiveKm / speedKmh
// 保守化：推荐值 ×1.08，区间 [est, est×1.2]（取慢侧）
```

### ③ VO2max 粗略兜底

```js
vVo2Kmh = 3.5 + 0.3 × VO2max   // 理论值
sustainKmh = vVo2Kmh × 0.6     // 长距离仅 60% 可持续
base = (距离 / sustainKmh) × 爬升惩罚
// 十分保守：推荐 ×1.8，区间 [×1.4, ×2.1]
```

### ④ 极端保守兜底

```js
// 通用越野速度带 3.5–5.0 km/h，推荐取慢侧 3.8
hours = distance / 3.8，区间 [d/5.0, d/3.5]
```

### 交叉校验（用户填时间时）

用户填了期望时间，引擎与能力画像估算做交叉校验：

```js
ratio = 期望时间 / 能力估算
ratio < 0.8   → 警告"可能过于激进"
ratio > 1.25  → 提示"总量偏宽松"
估算置信度 low 时不告警（避免保守兜底误导）
```

### 疲劳修正

```js
fatigue_risk  low→×0.96 / medium→×1.0 / high→×1.12 / severe→×1.18
// 只作用于 high/medium 置信度估算；low 置信度兜底保持原保守值
```

## 三、核心计算：碳水

```js
// 按时长分档（choTierBand）
< 45min → 0 / 45-75min → 0-30 / 1-2.5h → 30-60 / 2.5-3h → 60-90 / >3h → 60-90

// 上限（GI Constraint）
ceiling = min(90, verified_cho_max != null ? verified_cho_max : 60)
carbsPerHour = min(档位中值, ceiling)
dualSugar = carbsPerHour >= 60   // ≥60 强制双糖
totalCarbs = carbsPerHour × 完赛时间
```

## 四、核心计算：液体与钠

### 液体（实测汗率优先）

```js
if (实测汗率 sr > 0) {
  区间 = [0.65×sr, min(1.0×sr, 1.2)] L/h   // 上限钳制 1.2 L/h
  推荐 = 区间中点
} else {
  // 环境估算（低置信度）
  550 + max(0, 温度−15)×18 + max(0, 湿度−55)×3，钳制 [450, 1100]
}
```

### 钠（浓度 × 饮水量双指标）

```js
if (实测汗液钠) {
  流失(mg/h) = 汗液钠 × 饮水量(L/h)
  饮料浓度 = clamp(流失 / 饮水量, 400, 1000) mg/L
}
钠摄入(mg/h) = 浓度 × 饮水量
// 多来源叠加上限 1000 mg/h（超限告警）
```

## 五、核心计算：咖啡因

```js
预算 = 体重 × [3, 6] mg
caffeineTier: finishTime < 4h → "optional" / 4-6h → "late" / ≥6h → "staged"
// 独立模块，只给预算与分档，具体时点由 AI 安排
```

## 六、核心计算：补给点排程

补给点 = **CP ∪ 爬升触发点 ∪ 陡坡预补给 ∪ 时间兜底点**：

```js
// 爬升触发：累计爬升每满 climb_trigger_m（默认 250m）设一点
// 时间兜底：每 max_interval_min（默认 30min）设一点
// 时间窗合并：到达时间差 ≤15 分钟视为同一补给时刻（15min 内无法再有意义地摄入）
//   → 合并时优先保留真实 CP（物理点）
// 每点分配：总量 / 有效点数（碳水/液体/钠各一份）
```

补给点输出示例：

```js
{ km: 12.0, time_h: 1.42, carbs_g: 61.0, fluid_ml: 340, sodium_mg: 120, source: "cp+time_fallback" }
```

## 七、输出：数值契约 JSON

引擎输出带 `contract_version = "trail_lab_rule_contract_v2"` 的契约，四类内容 + 追踪数据：

```jsonc
{
  "contract_version": "trail_lab_rule_contract_v2",
  "engine_version": "2.0.0",
  "user_profile": { /* 画像（含 confidence） */ },
  "race_profile": { /* 线路（含 segments） */ },
  "engine_outputs": {
    "estimated_finish_time_h": 6.5,
    "finish_time_range": [5.9, 7.2],
    "finish_time_source": "user_input | engine_estimate",
    "debug_trace": {
      "finish_time_branch": "terrain | itra_fallback | ...",
      "terrain_completeness": { "ok": false, "missing": ["下降"] },
      "finish_breakdown": { "climb_h": 2.1, "descent_h": 0, "flat_h": 4.4 },
      "cho": { "ceiling": 75, "tier_range": [60, 90] }
    },
    "carbs_per_hour_g": 75, "carb_range_g": [60, 90],
    "fluid_per_hour_ml": 680, "fluid_range_ml": [550, 850],
    "sodium_mg_l": 600, "sodium_per_hour_mg": 480,
    "caffeine_budget_mg": [210, 420],
    "total_carbs_g": 487.5, "total_fluid_ml": 4420, "total_sodium_mg": 3120,
    "fueling_points": [ /* 补给点数组 */ ],
    "evidence": { "carbs": ["B5","A7"], "fluid": ["A5"], "sodium": ["A4","A2"], "caffeine": ["A8"] },
    "confidence": { "carbs": "high", "fluid": "high", "sodium": "low", "finish_time": "medium" },
    "warnings": [ "钠为保守区间，建议实测汗液钠浓度提高置信度", ... ]
  }
}
```

### `debug_trace`：为什么是这个数

引擎不只给结果，还把**怎么算的**写进契约：
- `finish_time_branch`：完赛时间走哪条估算分支
- `terrain_completeness`：地形数据完整度（缺哪些）
- `finish_breakdown`：爬升/下降/平路各占几小时
- `cho.ceiling`：碳水上限卡在哪个已验证值

AI 解释"为什么是这个数"时直接引用 `debug_trace`，用户也能逐行核对——**不必信任引擎内部发生了什么**。

## 八、Golden Cases：每版必过

用固定输入验证输出是否与期望一致，防止改坏旧功能。G1-G12：

| # | 用例 | 期望输出 |
| --- | --- | --- |
| G1 | 55km/3500m/6.5h/verified 75 | 总碳水 487.5g，20-30min 拆点 |
| G2 | 600mg/L × 0.8/1.2 L/h | 480/720 mg/h（双指标） |
| G3 | 汗率实测 1.08 L/h | 输出区间且不触发体重上限 |
| G4 | 65kg 咖啡因 | 预算 195-390mg，按赛程分档 |
| G5 | 无汗率/无汗钠 | 保守区间 + low + 实测校准提示 |
| G6 | CP 关门早于预估到达 | 关门警告 + 携带量提示 |
| G7 | 配速远超 VO2max 理论区间 | "可能高估"警告；置信度降 medium |
| G8 | 地形分类（陡坡/平路/下坡） | 按坡度阈值正确分桶；爬升用 VAM |
| G9 | hrvStatus=极差 | fatigue_risk=severe；区间放宽 ±15% |
| G10 | 普通训练文件无 HR | 不拒绝：分布分位数锚定，medium |
| G11 | BMI<16 或 >35 | warnings 营养/健康风险；数值不受影响 |
| G12 | 实测与 ITRA 推算差异>15% | 以实测为准；提示 ITRA 可能滞后 |

## 九、调用方式

## 十、工程化系数清单（全部"待实测校准"）

| 系数 | 值 | 用途 |
| --- | --- | --- |
| 爬升惩罚系数 | `1 + clamp((爬升率−30)/120, 0, 0.6)` | 完赛时间爬升惩罚 |
| ITRA 速度映射 | `7.0 + (PI−300)×0.005` | ITRA 兜底 |
| ITRA 保守化 | 推荐 ×1.08，区间 [×1, ×1.2] | ITRA 兜底取慢侧 |
| VO2max 可持续比 | 0.6，保守 ×1.8 | VO2max 兜底 |
| 平路当量 q | 8 m 水平 / 1 m 垂直 | 平路距离折算 |
| 液体上限 | min(1.0×汗率, 1.2 L/h) | 液体钳制 |
| 温度修正 | +18 mL/h/°C（>15°C） | 环境估算 |
| 湿度修正 | +3 mL/h/%（>55%） | 环境估算 |
| 补给合并窗 | ≤15 分钟 | 补给点合并 |

> ⚠️ 以上均为工程化推导系数，需在真实赛事中逐步实测校准；未经校准前在契约中标注"待实测校准"。

## 十一、局限

- 当前实现以 ≤70km / ≤5000m 为主；100km+ 战术化分支仅预留接口
- VO2max、ITRA 依赖手动输入（活动 FIT 文件不含）
- 出汗率、汗液钠实测门槛高
- 当前版本默认不存储用户数据，校准闭环受限为会话内
